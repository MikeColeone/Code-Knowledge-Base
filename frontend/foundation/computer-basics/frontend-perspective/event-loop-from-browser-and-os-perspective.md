# 从浏览器到操作系统视角理解 Event Loop

## 核心答案

前端讲 Event Loop 不能只停留在“宏任务和微任务”。更完整的说法是：浏览器主线程不断从任务队列里取任务执行，而定时器、I/O、用户输入、渲染时机这些异步来源，背后都和浏览器线程调度以及操作系统事件通知机制有关。

## 前端视角的理解方式

- JS 是单线程执行任务的。
- 异步能力不是 JS 引擎单独完成的，而是浏览器和操作系统一起提供的。
- 浏览器把定时器、网络、事件等结果在合适时机塞回任务队列。
- 微任务会在当前宏任务结束后、渲染前优先清空。

## 为什么这个问题会被追问

面试官想看你是否知道：`setTimeout` 不是到点立刻执行，而是到点后进入队列等待；网络请求回调也不是“自己突然执行”，而是由底层事件完成后再调度回主线程。

## 和性能的关系

- 微任务堆积过多，会推迟渲染。
- 宏任务太重，会造成长任务和卡顿。
- 不理解调度顺序，很容易写出看似异步、实际阻塞体验的代码。

## 常见追问

- `Promise.then` 为什么通常比 `setTimeout` 更早执行。
- `requestAnimationFrame`、微任务、渲染三者先后顺序是什么。
- Node.js Event Loop 和浏览器 Event Loop 有什么不同。
