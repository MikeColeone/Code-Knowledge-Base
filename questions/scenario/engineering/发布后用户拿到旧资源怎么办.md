# 发布后用户拿到旧资源怎么办

## 背景

前端发布完成后，常见问题不是“资源没发上去”，而是“部分用户还在访问旧 HTML、旧 JS 或混合资源”。这类问题会直接导致页面异常、接口不兼容或白屏。

## 目标

- 避免新旧资源混用
- 出现旧资源命中时能快速定位原因
- 让更新过程对用户尽量平滑

## 方案

### 资源治理原则

- `index.html` 或入口文档禁强缓存，保证入口尽快更新。
- JS/CSS/图片等静态资源使用内容哈希文件名，允许长缓存。
- 发布时保证先上传静态资源，再切入口引用，避免入口先切、资源未到。

### 常见问题链路

1. 用户拿到旧 HTML，继续引用旧 JS。
2. 用户拿到新 HTML，但 CDN 边缘节点还没同步到新 JS。
3. 本地有 Service Worker、离线缓存或旧 manifest。
4. 多页签并存，新旧版本同时活动。

### 处理方式

- 在入口里做版本比对，发现有新版时提示用户刷新。
- 对关键接口增加前端版本号，快速判断是不是版本错配。
- 如果系统使用 Service Worker，要设计明确的更新与失效策略。
- 发布系统保留最近几个版本的静态资源，避免旧页面引用直接 404。

## 技术取舍

- 所有资源都不缓存能减少错配，但会显著影响性能。
- 入口不缓存、静态资源强缓存是常见平衡点。
- 强制自动刷新体验差，但在强一致业务里可作为最后兜底。

## 异常和兜底

- 新旧接口不兼容：接口层保持一段兼容窗口，避免前端刚发版就炸。
- 旧资源 404：保留最近几个版本的产物，给旧页面留缓冲时间。
- 用户多页签：可通过 `BroadcastChannel` 通知其存在新版本。
- Service Worker 污染：提供手动清缓存方案，并在发布时谨慎升级缓存 key。

## 监控和验证

- 监控静态资源 404、HTML 命中率、资源版本分布。
- 在日志里带上前端版本号和资源清单版本号。
- 灰度发布时重点检查入口和静态资源是否来自同一版本。
- 线上排障时先确认用户命中的 HTML 版本、JS 文件名和接口版本。

## 面试追问

- 为什么前端常说“HTML 不缓存，静态资源强缓存”？
- 如果用户一直不刷新页面怎么办？
- 如果用了微前端，子应用资源版本如何治理？
