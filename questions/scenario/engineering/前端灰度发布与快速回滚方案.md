# 前端灰度发布与快速回滚方案

## 背景

前端发布虽然比服务端轻，但一旦静态资源或核心逻辑出错，影响范围往往很大。纯全量发布风险高，纯人工回滚又慢，所以需要一套能逐步放量、快速止损的发布机制。

## 目标

- 先小流量验证，再逐步放量
- 出现异常时能快速止损和回滚
- 能追踪用户当前命中的前端版本
- 尽量不影响正常用户访问

## 方案

### 核心思路

- 静态资源使用内容哈希文件名，保证版本可区分。
- HTML 入口或配置接口负责决定用户命中哪个版本。
- 按用户维度灰度，而不是按请求随机灰度，避免用户来回切版本。
- 所有前端错误、性能指标和埋点都要带上版本号。

### 常见灰度方式

1. 网关或 CDN 层按 Cookie、UID、Header 做流量分桶。
2. HTML 模板根据灰度规则返回不同资源清单。
3. 通过配置中心切换资源入口，实现快速回滚到上一版本。

### 回滚策略

- 资源层回滚：切回上一版 HTML 或配置。
- 开关层回滚：快速关闭风险功能。
- 业务层回滚：接口兼容未就绪时切回旧链路。

## 技术取舍

- 直接覆盖旧资源发布最简单，但回滚困难且缓存风险大。
- 保留多版本资源成本更高，但排障和回滚效率明显更好。
- 前端自带功能开关很灵活，但不能替代版本治理，两者最好同时存在。

## 异常和兜底

- 新版本白屏：立即切回上一版入口，并根据版本号排查错误日志。
- 部分用户命中新版接口不兼容：通过灰度开关切回旧接口路径。
- 缓存污染：入口 HTML 禁强缓存，静态资源走强缓存加哈希。
- 回滚后仍有用户异常：检查 Service Worker、本地缓存和 CDN 边缘缓存是否残留旧规则。

## 监控和验证

- 监控每个版本的 JS 错误率、白屏率、接口失败率、核心性能指标。
- 灰度放量建议按 `1% -> 5% -> 20% -> 50% -> 100%`。
- 每一阶段都验证核心链路：登录、首屏、提交、支付或关键业务动作。
- 保留版本与构建产物的映射关系，方便快速定位 commit。

## 面试追问

- 如果前端已经全量，怎么做到秒级回滚？
- 如果多个微前端子应用版本不一致怎么办？
- 如果用户刷新后在新旧版本之间来回切怎么办？
