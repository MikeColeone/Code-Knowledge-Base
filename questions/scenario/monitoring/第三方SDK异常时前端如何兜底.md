# 第三方 SDK 异常时前端如何兜底

## 背景

埋点、客服、地图、风控、登录、支付这类能力经常依赖第三方 SDK。一旦对方加载失败、初始化超时或运行时报错，轻则部分功能失效，重则拖垮主链路。

## 目标

- 第三方 SDK 挂掉时不影响核心业务流程
- 能快速发现、隔离和止损
- 保留必要的降级能力和补偿方案

## 方案

### 分级治理

- 核心链路依赖：如登录、支付，必须有服务端兜底或备用方案。
- 非核心依赖：如埋点、客服，可降级为静默失败或延迟加载。
- 装饰型依赖：如动效、辅助组件，必要时直接关闭。

### 接入原则

- SDK 初始化放在适当时机，不要一上来全部阻塞首屏。
- 所有第三方调用统一走一层适配器，不要在业务代码里直接散调。
- 对初始化和关键调用做超时控制。
- 提供开关能力，必要时可以远程关闭。

### 降级方案

- 加载失败：记录错误并降级到本地占位能力。
- 初始化超时：终止等待，走兜底逻辑。
- 运行时报错：捕获异常，隔离当前功能模块，避免影响全局。

## 技术取舍

- 直接脚本注入接入快，但治理能力弱。
- 统一适配层初期开发量更高，但后续切换供应商、做熔断和监控更方便。
- 把第三方能力完全做成同步强依赖风险很高，非必要不要卡主主流程。

## 异常和兜底

- 支付 SDK 失败：给出重试按钮或切换备用支付方式。
- 登录 SDK 失败：保留账号密码登录或短信登录。
- 埋点 SDK 失败：先本地缓存，恢复后再补发，或者直接允许丢失非关键埋点。
- 地图 SDK 失败：退化为静态地址信息。

## 监控和验证

- 监控脚本加载成功率、初始化成功率、关键方法调用成功率。
- 埋点区分是第三方问题、网络问题还是业务代码问题。
- 对远程开关做灰度验证，保证能快速关闭高风险依赖。
- 重点观察第三方失败是否带来主线程阻塞、白屏或主流程中断。

## 面试追问

- 如果第三方 SDK 自己内部报错，把全局脚本打崩了怎么办？
- 哪些 SDK 可以失败，哪些不可以？
- 如果要更换供应商，怎么降低业务改造成本？
