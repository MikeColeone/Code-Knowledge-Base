# 大批量 DOM 更新与事件委托怎么设计

## 背景

一些高频交互场景，比如评论流、可编辑列表、树结构、拖拽面板，都会遇到大量节点更新。如果直接逐个操作 DOM，很容易出现卡顿、重排频繁和事件管理混乱的问题。

## 目标

- 降低大量 DOM 变更带来的性能损耗
- 避免成百上千个节点分别绑定事件
- 保证复杂交互下的代码可维护性

## 方案

### 批量更新 DOM

- 先在内存中构建节点，再一次性插入页面。
- 使用 `DocumentFragment`、模板字符串、批处理更新减少真实 DOM 操作次数。
- 对大列表做分片渲染，把长任务切成多个小任务，避免主线程长期阻塞。

### 事件委托

- 把点击、输入、选择等事件统一挂在父容器上。
- 在事件回调中通过 `event.target`、`closest` 判断真实命中的子节点。
- 对动态增删节点的场景，事件委托比逐个绑定更稳，因为新增节点不需要额外绑事件。

### 适用场景

- 评论列表操作按钮
- 树节点展开收起
- 表格行内操作
- 富文本工具栏和画布元素交互

## 技术取舍

- 直接操作 DOM 更接近底层，适合高性能局部场景，但维护复杂度高。
- 框架驱动渲染维护成本更低，但极端场景下仍要理解底层批处理和事件机制。
- 事件委托能减少监听器数量，但在 `focus`、`blur` 这类不冒泡事件上要额外处理。

## 异常和兜底

- 节点层级复杂：优先使用 `closest('[data-action]')` 这类方式查找目标节点。
- 大量插入导致卡顿：做分批插入或虚拟列表，不要执着一次性全部渲染。
- 委托范围过大：只在合理容器上做代理，避免全局 document 监听难以维护。
- 事件目标不稳定：通过 `data-*` 标记交互意图，而不是依赖样式类名。

## 监控和验证

- 用 Performance 面板观察长任务、布局抖动和样式重算。
- 对比逐条插入和批量插入的耗时差异。
- 统计列表大小增长时的交互延迟和滚动 FPS。
- 高频交互场景下关注监听器数量和内存占用。
